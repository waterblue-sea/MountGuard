# 🛡️ MountGuard：挂载自愈与安全软重启模块

专治 **临时 Root / 软重启玩家** 的各种“玄学漏 Root”：明明刚开机提权时 Momo 全绿、学信网正常使用，结果**软重启几次之后，Momo 突然提示「发现 Magisk」，学信网等软件直接报 Root 环境罢工**；甚至把可疑模块卸载了再软重启都没用，非得删光 `/data/adb` 硬重启才能恢复。

如果你也遇到过这个让人抓狂的死循环，这个模块就是为你写的。

---

## 📖 起因：一次真实的踩坑破案

我的主力机是 OPPO Find X8 Ultra（ColorOS），通过提权获取临时 Root（配合 KernelSU + NyaZygisk + Vector + HMA）。按理说这套组合拳隐藏效果极佳，但只要我在日常使用中执行几次**软重启**（用来激活模块或重启服务），Root 隐藏就会瞬间全面崩盘。

最诡异的是：
1. 哪怕我把新刷的温控/高刷模块删掉并再次软重启，Momo 依然死咬着“发现 Magisk”不放；
2. 抓出进程树看，NyaZygisk 和 HMA 都在正常运行，根本没有掉线；
3. 直到扒开 `/proc/1/mountinfo`（PID 1 全局挂载表），我才看到了极其离谱的一幕——仅仅软重启了 2 次，我的挂载表里居然炸出了 **141 行**指向 `/data/adb/modules/...` 的重复挂载，甚至有 **45 行直接挂载到了 `/data/adb/modules/` 文件夹自己头上**！

---

## 🔍 原理解析：为什么软重启几次就会“引爆”挂载表？

很多用正规 Root（直接刷 `boot` / `init_boot`）的朋友可能一辈子不会遇到这个问题，但在**临时 Root + ColorOS 等定制系统**下，这是一个 100% 必现的 Linux 内核 VFS（虚拟文件系统）机制陷阱。

### 1. 为什么偏偏是高刷、分辨率、温控模块出事？
对于标准的 `/system`、`/vendor`、`/product` 分区，KernelSU 的原生守护进程 `ksud` 会用干净的 `OverlayFS` 统一接管挂载，并且严格做好了命名空间隔离。

但是像 ColorOS / RealmeUI / OxygenOS 这类系统，高刷、分辨率、温控配置文件全放在专有的 `/my_product` 和 `/my_stock` 分区里。KernelSU 默认不自动挂载这些非标分区，所以几乎所有改温控、改高刷模块的作者，都会在 `service.sh` 或 `post-fs-data.sh` 里手写最原始的绑定挂载命令：
```sh
mount --bind /data/adb/modules/xxx/refresh_rate_config.xml /my_product/etc/refresh_rate_config.xml
```
包括像 `zygisk_vector` 挂载 `/apex/com.android.art/bin/dex2oat64` 时，用的也是同样的裸 `mount --bind`。

### 2. 第一阶段：首次提权挂载 ＝「埋雷」
在安卓系统中，`/data` 分区默认带有共享传播属性（比如 `shared:59`），而且为了保证所有软件读写数据一致，**全手机所有 App 的沙盒空间（包括 NeoZygisk 专门备份的“干净挂载命名空间”）里的 `/data` 分区，全都连在同一个 `shared:59` 共享组里**。

而系统原生的 `/my_product` 分区默认是私有挂载（`private`）。
* 当你开机**第 1 次**提权并运行模块脚本时，把 `/data/adb/...` 下的文件绑定挂载到 `/my_product/...` 上：
* 因为此时的目标点 `/my_product` 是私有的（`private`），内核不会向外广播这次挂载。所以此时 `/data/adb` 上没有任何反向残留，Momo 和学信网什么都查不到，一片全绿。
* **但致命的雷已经埋下了：** 因为挂载源来自 `/data`（`shared:59`），新挂载上去的这个 XML 文件节点，**自动继承并变成了 `shared:59` 属性**！

### 3. 第二阶段：软重启重跑脚本 ＝「指数级引爆」
正规 Root 用户刷完模块习惯直接“硬重启”，断电瞬间内核 RAM 里的挂载表直接清零，每次开机脚本永远只跑第 1 次（埋雷但不引爆）。

而**临时 Root 用户不能硬重启**（硬重启会掉 Root），每次激活环境或调试模块都要靠**软重启**。软重启只杀了用户空间的 `zygote`，**Linux 内核根本没重启**！当软重启脚本第 2 次执行那句 `mount --bind` 时：
1. **跨命名空间反向传染：** 此时目标文件顶层已经不再是 `private`，而是上一次留下的 `shared:59`！往一个 `shared:59` 的节点上再次挂载，Linux 内核会触发共享子树广播（`propagate_mnt`），把这次挂载**强行克隆同步给 `shared:59` 里的所有成员**——于是，这个挂载被内核顺着网线**反向挂载到了 `/data/adb/modules/...` 自己身上**！
2. **击穿一切 Zygisk 隐藏：** 因为 `/data` 分区在所有命名空间里共享，这个反向打回 `/data/adb` 的挂载会**直接穿透进 NeoZygisk 的干净命名空间以及所有 App 的命名空间**。而无论是 KernelSU 还是 NeoZygisk，卸载模块时只卸载 `/system`、`/vendor` 等系统目录，绝不会去卸载 `/data` 分区！
3. **$2^k$ 指数级叠罗汉：** 更恐怖的是，每一次重复 `mount --bind`，都会在已有的每个 `shared:59` 节点上再套一层，且新层继续加入 `shared:59`。设重入次数为 $k$，三个路径（`/my_product`、`/mnt/vendor/my_product`、`/data/adb`）上的挂载层数会按 $(2^k, 2^k, 2^k - 1)$ 指数爆炸：
   * **首次激活（$k=0$）：** `1 层, 1 层, 0 层`（完美潜伏）
   * **第 1 次软重启（单文件挂载 2 次，$k=2$）：** `4 层, 4 层, 3 层`（已开始向 `/data/adb` 漏毒）
   * **第 2 次软重启（$k=4$）：** `16 层, 16 层, 15 层`（单个文件炸出 47 层，3 个文件就是 141 层！）

此时任何软件只要读一眼 `/proc/self/mountinfo`（普通权限即可读取），就能看到满屏的 `/data/adb/modules/...`。Momo 看到直接报“发现 Magisk”，学信网底层 Native 安全 SDK 看到直接报“Root 环境”（HMA 只拦应用列表，拦不住 `mountinfo` 泄漏）。

### 4. 为什么卸载了模块再软重启也没用？
因为你在管理器里点卸载（或删文件夹），只是删了硬盘上的文件。**之前炸出来的 141 层挂载还死死钉在 Linux 内核的内存（VFS 树）里，没有任何人替它执行 `umount`！** 甚至因为硬盘文件被删而内存挂载还在，内核还会在路径后面打上刺眼的 `//deleted` 标记，检测软件抓得更准。

## 🛠️ MountGuard 是如何一劳永逸解决的？

不需要你挨个去改第三方模块的脚本，也不需要每次排查是谁干的。`MountGuard` 直接从 `/proc/1/mountinfo` 的底层拓扑结构入手，自动完成四件事：

1. **精准拔除 `/data/adb` 反向自挂载毒瘤：**
   自动扫描所有挂载源来自 `/adb/modules/` 且挂载点落在 `/data/adb/` 自身的异常项，无条件循环 `umount -l` 剥离清零。
2. **削平 $2^k$ 套娃堆叠，保留唯一有效层：**
   检测到模块在 `/my_product`、`/mnt/vendor`、`/apex` 等目录堆叠了多层挂载时，自动剥离冗余层，精确只留 `1` 层，保证温控/高刷模块功能正常生效的同时不留累赘。
3. **自动注射 `MS_PRIVATE` 隔离疫苗（核心）：**
   对所有来自 `/data/adb/modules/` 的绑定挂载强制执行 `mount --make-private`。直接把第一层挂载从 `shared:59` 剥离为私有态，从物理上斩断它向 `/data` 分区反向传染的通道。哪怕烂模块以后再重跑 100 次裸 `mount --bind`，也再也炸不出反向挂载。
4. **自动超度已卸载/已禁用模块的僵尸挂载：**
   每次运行自动核对 `/data/adb/modules/<模块名>` 下的 `remove` 或 `disable` 标记。只要你在管理器里关掉或卸载了某个模块，点一下本模块的执行按钮（或软重启），立刻替它在内核内存里完成 `umount` 清理，告别“卸载不生效”。

## 🚀 使用方法

刷入本模块后，它会在两个地方为你工作：

### 1. 自动后台巡检（无感守护）
每次开机或软重启触发 `service.sh` 时，模块会自动扫描修复全局挂载表，并在后台延迟 `5s / 15s / 30s` 进行三次补刀巡检（专门对付那些喜欢在脚本里写 `sleep 20` 之后再偷偷执行裸 `mount --bind` 的温控模块）。

### 2. 管理器内置「执行 (Action)」按钮（热修复 & 安全软重启）
打开 KernelSU / APatch 管理器的模块页面，找到 **MountGuard**，直接点击卡片上的 **【执行】** 按钮：
* **只修复不重启（默认）：** 点击【执行】后什么键都不用按，0.5 秒内当场扫平所有泄漏挂载，等待 4 秒自动退出。此时清掉检测软件缓存重新打开，无需重启直接过检！
* **一键安全软重启：** 点击【执行】后，在 **4 秒内按一下「音量+」键**，模块会自动清理已卸载模块残留、重启 `zygote`，并在桌面重新加载后自动完成两轮挂载消杀。

## 📊 效果对比：自己动手验证

在 Termux（Root 权限）下运行以下命令查看全局挂载表中的模块痕迹：
```sh
grep -E "adb" /proc/1/mountinfo
```
* **使用前（软重启 2 次后）：** 刷屏一百多行，满屏 `shared:59` 以及挂载在 `/data/adb/modules/...` 自己头上的泄漏记录。
* **使用 MountGuard 后：** 瞬间缩减为干净的单层挂载，`/data/adb/` 自挂载记录为 `0`，且所有模块挂载行的 `shared:XX` 标记彻底消失！

## 📦 目录结构与自行打包

如果你想直接打包本仓库源码：
```text
MountGuard/
├── module.prop       # 模块基础信息
├── common_func.sh    # VFS 挂载表扫描、消杀与 private 隔离核心逻辑
├── service.sh        # 启动自愈与 5s/15s/30s 延迟巡检守护
└── action.sh         # 管理器【执行】按钮交互（支持在线热修复与音量+安全软重启）
```
将上述 4 个文件直接（不带外层文件夹）压缩为 `.zip`，即可在 KernelSU / APatch 管理器中刷入。
